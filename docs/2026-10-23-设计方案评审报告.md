## 一、设计方案评审

### 1.1 产品定位

**评价：合理，但需明确差异化边界。**

产品定位是"GitHub Desktop 级版本控制 + 多仓库编排 + 声明式发版流水线"，切中的真实痛点是：多仓库/多组件项目在 GitHub Desktop、Fork、SourceTree 等工具中缺乏"组件级"抽象（一个仓库里的 Web 前端 + API 后端被当作一个整体提交）。竞品中.lazygit / Fork / Sublime Merge 均无组件地图与发版流水线概念，**差异化成立**。

风险点：定位同时覆盖"精细版本控制"和"编排/流水线"两条战线，建议明确 **MVP 边界**（见 4.5 里程碑），避免首发功能过重。

### 1.2 技术架构（.NET 8 + WPF 路线）

| 层 | 设计内容 | 评价 |
|---|---|---|
| 表现层 | WPF + WPF-UI（Fluent） | ✅ 可行。WPF-UI（lepoco/wpfui）MIT 协议，支持 .NET 8，文档所需的 `ContentDialog`、`InfoBar`、`Snackbar` 均有现成控件。风险：社区项目 3.x 系列 API 变动较频繁，**必须锁定版本号**。 |
| 引擎层 | LibGit2Sharp（本地高频）+ Git CLI（网络/复杂） | ✅ 方向正确的混合边界策略，但有两个设计缺陷，见 1.3。 |
| 调度层 | 全局任务队列，同仓库写串行、跨仓库读弱并行 | ✅ 模型正确，但缺少"取消/超时/重试"语义，见 1.3。 |
| 存储层 | SQLite + DPAPI | ✅ 可行，但需明确"什么不进数据库"，见 1.3。 |

### 1.3 架构层需要补充的关键设计（评审发现问题）

**问题 A（🔴 高）：双引擎写冲突未定义。**
LibGit2Sharp 与 Git CLI 操作**同一个工作区的 `.git` 目录**。CLI 侧的 `rebase`、`gc`、hook 脚本若与 LibGit2Sharp 的 index 写入并发，会产生 index.lock 冲突甚至索引损坏。设计稿只说了"按操作类型分流"，没有说"按**同一仓库内的时刻互斥**分流"。
**解决方案**：所有针对同一仓库的操作（无论走哪个引擎）都经过同一把**每仓库互斥锁**（`SemaphoreSlim(1,1)`）；CLI 只读命令统一加 `--no-optional-locks`；引擎选择是"锁内选路"而不是"锁外分流"。

**问题 B（🔴 高）：行级暂存的技术路径未落地。**
设计稿承诺"行级/Hunk 级勾选暂存"，但 **LibGit2Sharp 的 index API 不支持直接按行写入**。GitHub Desktop 的实现方式是：自行构造部分补丁（patch）后应用到 index。这在 WPF 侧是一项独立的、工作量不小的子工程。
**解决方案**：MVP 先交付 Hunk 级（块级）暂存——用 LibGit2Sharp 生成 patch、按 hunk 切片、重组 patch 后 `git apply --cached` 语义写入；行级暂存降级为 M3+ 特性，并在 UI 上先隐藏。

**问题 C（🟡 中）：调度层缺少失败语义。**
任务队列未定义：取消（用户点停止 → `CancellationToken` 传播到 CLI 子进程 kill）、超时（hung 进程的看门狗）、重试（网络类操作幂等重试策略）、进程输出背压（大量输出时的缓冲策略）。
**解决方案**：任务对象统一实现 `ICancelable`；CLI 子进程启动即注册超时看门狗（默认 10 分钟可配置）；输出走 `Channel<string>` 流式消费，避免 UI 绑定卡顿。

**问题 D（🟡 中）：存储层未划定边界，存在"缓存腐化"风险。**
若把 Git 状态（分支、脏文件、Ahead/Behind）缓存进 SQLite，后台 git 操作会使缓存失效，UI 显示将不可信。
**解决方案**：**Git 实时状态一律不落库**，每次进入视图时由引擎现查（配合 FileSystemWatcher 节流刷新）。SQLite 只存：项目/仓库清单与分组、组件地图（扫描结果 + 手动修正）、流水线配置、凭据引用、用户偏好。

### 1.4 核心功能域评审

1. **工作空间与仓库管理**：✅ 无技术争议。"批量 Pull/Push 预演"（Bulk Dry Run）设计良好，是差异化亮点。
2. **动态组件识别**：🟡 "扫描标记文件与依赖树"的**识别规则本身没有定义**。建议在文档补充规则表初版：`package.json` → 前端/JS 组件；`*.csproj` → .NET 组件；`Dockerfile` → 容器镜像；`pom.xml`/`go.mod` → 后端；识别结果必须可手动修正并持久化（设计稿已提到，保持）。
3. **版本控制工作台**：见问题 B；"Hooks 透明执行"注意 CLI 路线天然支持，LibGit2Sharp 路线**不会执行 hooks**，凡涉及 commit 一律走 CLI 或显式补 hook 调用，否则用户 hook 会静默失效（🔴 必须写进开发规范）。
4. **版本发布与流水线**：Conventional Commits 推导版本可行（`feat`→minor、`fix`/`perf`→patch、`!` 或 `BREAKING CHANGE:` footer→major）；**多组件提交**（一次 commit 跨前端+后端）如何 bump 需补充规则：按组件地图路径前缀归属，跨组件 commit 触发多组件联合 bump 并在审阅弹窗中明确列出。多组件 Tag 必须带前缀（`web-v1.4.2`）避免同一仓库内 Tag 冲突。
5. **CI/CD 聚合**：🟡 `nektos/act` 强依赖本机 Docker Desktop，且对部分 GitHub Actions 语法/action 兼容不全。必须做成**能力可选**：启动时探测 Docker，不可用则禁用本地模拟按钮并给出引导文案，而不是报错。`gh cli` 同理需探测安装与登录态。

## 二、技术可行性分析

| # | 技术点 | 结论 | 说明与前提 |
|---|---|---|---|
| 1 | .NET 8 + WPF + WPF-UI | ✅ 可行 | 锁定 WPF-UI 版本；自绘控件（任务进度球、组件徽标）用 `ControlTemplate` 扩展而非第三方皮肤 |
| 2 | LibGit2Sharp 本地操作 | ✅ 有条件可行 | 维护模式项目但生态成熟；注意 win-x64 原生二进制随发布包分发（self-contained 发布验证）；超大仓库 status 性能劣于 CLI，预留"CLI 降级开关" |
| 3 | Git CLI 互操作 | ✅ 可行 | 输出解析统一用 `--porcelain=v2`；加 `-c core.quotepath=false` 处理中文文件名；编码按字节读取后按 UTF-8 解码，防 GBK 乱码 |
| 4 | 行级暂存 | ⚠️ 高成本 | 见问题 B，建议降级为 Hunk 级先行 |
| 5 | 同仓库写串行调度 | ✅ 可行 | `System.Threading.Channels` + 每仓库锁 + 全局并发上限（建议默认 4） |
| 6 | SQLite（Microsoft.Data.Sqlite） | ✅ 可行 | 开 WAL 模式；架构见 1.3 问题 D 边界 |
| 7 | DPAPI 凭据加密 | ✅ 可行 | `System.Security.Cryptography.ProtectedData`，CurrentUser 作用域；Git 推拉凭据交给 Git Credential Manager，应用只存自己的 GitHub PAT/API token |
| 8 | Conventional Commits 推导 | ✅ 可行 | 补多组件规则（1.4-4） |
| 9 | act 本地模拟 | ⚠️ 有条件可行 | Docker 强依赖 + 兼容性缺口；做成可选能力 + 引导安装 |
| 10 | gh cli 远程触发 | ✅ 有条件可行 | 需探测安装与 auth 状态，未安装时给出引导链接 |
| 11 | Windows 环境适配 | 🟡 需显式设计 | ① 长路径（>260 字符）：manifest `longPathAware` + `AppContext.SetSwitch`；② 中文/空格路径全链路测试；③ 单实例互斥量；④ 未签名 exe 的 SmartScreen 提示（首发可接受，后续考虑代码签名）；⑤ 自动更新建议引入 Velopack（Squirrel 后继） |

**总体可行性结论**：无不可逾越的技术障碍。两个高成本点（行级暂存、act 兼容）均可用"降级交付 + 可选能力"化解。

## 四、优化与补充建议

### 4.1 仓库骨架调整（高优先）

```text
apps/windows/
├── ProjectManager.sln
├── src/
│   ├── ProjectManager.App/          # WPF 入口（表现层）
│   ├── ProjectManager.Core/         # 引擎层（Git 引擎抽象、调度器、组件识别）
│   ├── ProjectManager.Storage/      # SQLite + DPAPI
│   └── ProjectManager.CliInterop/   # Git CLI / gh / act 进程封装
└── tests/
    ├── Core.Tests/
    └── CliInterop.Tests/            # 进程封装必须有真 git 仓库的集成测试
```

`packages/` 四个子包当前无消费方（单 App 无跨端复用需求），建议合并为 `src/` 内项目，待真正出现第二端再抽包——避免骨架先行导致的维护税。

### 4.2 性能设计补充

- **UI 虚拟化**：历史列表、文件树、任务列表必须 `VirtualizingStackPanel`（万级提交不卡）。
- **Diff 渲染窗口化**：仅渲染可视区行；单文件 Diff 超 5000 行时截断并提供"外部工具打开"。
- **仓库扫描节流**：FileSystemWatcher 事件 500ms 防抖合并；多仓库总览轮询间隔 ≥ 5s 且仅在窗口激活时轮询。
- **CLI 大输出**：流式读取，禁止 `ReadToEnd`。

### 4.3 健壮性与安全补充

- 所有 CLI 调用注入完整环境变量（`GIT_TERMINAL_PROMPT=0`），杜绝子进程挂起等待输入。
- Push/Pull 凭据走 Git Credential Manager；DPAPI 仅存应用级 token；**任何日志中不得出现 token/密码**（日志脱敏中间件）。
- 危险操作（Reset --hard、Discard、Force Push）双确认，其中 Discard 前自动生成 stash 快照（可恢复，对应文档 3.3 回滚弹窗的"查看将丢失的代码差异"）。

### 4.4 数据模型草案（SQLite 核心表）

```sql
workspace(id, name, sort_order)
repo(id, workspace_id, path UNIQUE, display_name, identity_profile)
component(id, repo_id, kind /*web|api|desktop|image*/, name, root_path, version_file, auto_detected bool, manual_override bool)
pipeline(id, repo_id, name, steps_json)
setting(key PRIMARY KEY, value_json)
```

Git 实时状态**不建表**（见 1.3 问题 D）。

### 4.5 里程碑建议（MVP 边界）

| 阶段 | 范围 | 出口标准 |
|---|---|---|
| M1 | 单仓库 Git 工作台：状态/暂存(Hunk 级)/提交/Hooks/历史/回滚 | 在含中文路径仓库上稳定日用 |
| M2 | 工作空间多仓库 + 组件识别 + 批量预演与执行 + 任务面板 | 10 仓库并发操作无死锁、可取消 |
| M3 | 发版流水线（推导/审阅弹窗/回写）+ CI/CD（gh 远程为主，act 可选） | 全流程演示走通（对照本次 P2 修订稿） |
