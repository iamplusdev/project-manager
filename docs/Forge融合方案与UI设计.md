## 0. 文档定位与范围

### 0.1 本文要回答的三个问题

1. **为什么融合**：Project_Forge 的「新建项目即生成规范结构」为什么应成为 Project_Manager 的入口级能力，而不是并列的独立工具。
2. **怎么整合**：用本项目的技术栈（.NET 8 + WPF + WPF-UI + LibGit2Sharp/Git CLI + SQLite + DPAPI）如何分层重写，与现有领域模型（项目 / 组件 / 仓库 / 发版）如何打通。
3. **UI 怎么设计**：主壳与「新建项目」向导的信息架构、布局、组件、状态、交互、异常态与 WPF-UI 控件映射。
4. **以什么形态引入**：独立软件还是整合进 PM（结论见 D4：**只做内嵌能力**，不发行独立软件）。

### 0.2 本文不做什么

- **不写实现代码**（按约定，编码在方案与 UI 评审通过后另行启动）。
- 不重复《软件设计方案 v2》已定稿的 Git 工作台、组件识别、发版流水线细节，仅说明与本能力的衔接点。
- 不改变 Project_Forge 的既有行为语义；融合以「行为等价 + 增量增强」为原则。

### 0.3 读者

产品/架构/UI/客户端开发。开发可直接依据第 3、4、5 节落地，UI 可直接依据第 6 节出图与评审。

## 1. 结论摘要（TL;DR）

| 维度 | 结论 |
|---|---|
| **融合定位** | 把 Forge 的「新建项目即生成结构」提升为 Project_Manager 的**入口级能力（Project Creation / Scaffolding）**，主壳顶部「新建项目」为主入口，生成结果直接成为 PM 的受管项目。 |
| **引入形态** | **形态选定：不保留独立 Forge 软件**。生成能力作为 PM 内嵌入口，引擎独立为 `ProjectManager.Scaffolding` 库，仅服务 PM 主程序一个宿主；不发行任何以 Forge 名义的独立安装包或独立 GUI。 |

| **行为等价** | 完整保留 Forge 的：模板驱动、模块勾选、幂等重跑、`.bak` 备份、`.gitignore` 保留、空目录 `.gitkeep` 占位、失败回滚、表单校验、深浅色。**等价判定以冻结快照为基线**（见 4.3 G0 与 9.1），不再依赖 Forge 在线可比。 |
| **增量增强** | 三步向导 + 生成前预览、模板 `files` 内容注入、命名派生、生成元数据、`git init`、项目即时注册与最近列表、组件候选白名单、模板热覆盖、10 类异常态与错误码体系。 |
| **关键决策** | 不引入 Python 运行时；`templates.json` 与 Forge **字段兼容**（可平滑迁移已有模板）；引擎独立成库、UI 只做编排；**Git 实时状态不落库**（沿用设计第 4 节）；**模板来源以用户目录为准**（`%APPDATA%` 优先，避免安装目录只读）。 |
| **已锁定决议** | D1 向导采用**独立 Window**；D2 首批**内置「单体桌面工具」模板**（共 3 套）；D3 **不保留** Forge 独立发行版；D4 **不做独立软件**（含第二个 GUI 与独立 CLI 发行物）。详见 8.2。 |
| **方案强化（v1.2）** | P0：等价基线快照化、模板来源三源修正、回滚不可中断、结果页语义修正、里程碑切分修正。P1：`files` 能力、`.pm-scaffold.json` 元数据、命名派生、组件白名单、错误码 + `schemaVersion`。 |
| **交付边界** | 本文交付方案与 UI 规格；编码按《开发计划（阶段制）》推进，阶段划分与出口标准不在本文重复。 |

## 2. 现状与差距分析

### 2.1 Project_Forge 现状（已实测）

- **形态**：Python 3 + CustomTkinter 单窗口桌面工具；`src/` 内已清晰分层（`main` / `app` / `generator` / `templates` / `validation`）。
- **能力清单**：
  - 两套模板：「全栈项目」（apps / contracts / packages / infra / output / assets / docs / scripts，含 4 个可选模块：Web 前端、后端服务、安卓 App、Windows 软件）、「轻量工具」（src / scripts / config / assets / docs / output）。
  - 表单校验：名称 ≤50 字、禁非法字符与 Windows 保留名、不以点结尾；简介 ≤200 字；生成路径存在且可写。
  - 生成语义：幂等重跑；`README.md`/`structure.md` 同名先备份 `.{yyyyMMdd-HHmmss}.bak`；已有 `.gitignore` 保留；空叶子目录写 `.gitkeep`，但被 `.gitignore` 忽略的目录跳过占位；失败回滚本次新建的空目录并清理占位文件。
  - 产物：`README.md`、`structure.md`（含目录树与逐目录中文说明）、`.gitignore`。
- **验证结论**：纯逻辑单测 36/37 通过（唯一失败为环境缺 `tkinter` 图形库，非代码缺陷）；端到端生成演练通过（全栈全模块、轻量工具、幂等重跑）。

### 2.2 Project_Manager 现状

- **形态**：Windows 桌面多仓库/组件编排与发版工具，设计方案 v2 已定稿；仓库目前仅有目录骨架，尚无 .NET 实现。
- **技术栈**：.NET 8 + WPF + WPF-UI；LibGit2Sharp + Git CLI 双引擎；SQLite（WAL）+ DPAPI；Velopack 打包。
- **已定稿的关键约束**（与本能力相关）：
  - 双引擎**每仓库互斥锁**（`SemaphoreSlim(1,1)`），CLI 只读命令加 `--no-optional-locks`；Hook 相关提交必须走 CLI。
  - **Git 实时状态不落库**；SQLite 只存项目/仓库清单、组件地图、流水线配置、凭据引用、用户偏好。
  - Windows 适配：长路径、中文路径、单实例、Velopack。
  - 性能：UI 虚拟化、Diff 窗口化、扫描节流。

### 2.3 差距与融合挑战

| 维度 | Forge | Project_Manager | 融合要解决 |
|---|---|---|---|
| 语言/运行时 | Python | .NET 8 | 能力用 C# 重写，不引入 Python 运行时 |
| UI 框架 | CustomTkinter | WPF + WPF-UI | UI 重画为 Fluent，统一主题与交互 |
| 架构 | 单进程分层 | 多项目分层（Scaffolding/App/Storage/CliInterop） | 引擎独立成库，UI 归 App，持久化归 Storage |
| 持久化 | 无 | SQLite + DPAPI | 最近项目/生成记录入库，路径脱敏 |
| Git 语义 | 仅文档提示「初始化 Git」 | 双引擎 + 互斥 | `git init` 走 CLI，纳入仓库清单 |
| 异常态 | 基本无 | 设计已要求异常/空/冲突态 | 补齐 10 类异常态（含错误码） |
| 领域衔接 | 无（独立工具） | 项目/组件/仓库/发版 | 生成即注册项目，顶层目录入组件候选 |

## 3. 方案整合（架构）

### 3.1 定位：从「独立工具」到「PM 入口能力」

```text
┌──────────────────────────────────────────────────────────────┐
│                     Project_Manager（单一产品）                │
│                                                              │
│  ① 新建项目（Scaffolding）  ← 由 Project_Forge 重构而来        │
│        │  生成规范骨架 + 注册为受管项目                        │
│        ▼                                                     │
│  ② 组件识别 / 仓库编排      ← 设计 v2 已定稿                   │
│        │                                                     │
│        ▼                                                     │
│  ③ Git 工作台（Hunk 级暂存） ← M1                            │
│        │                                                     │
│        ▼                                                     │
│  ④ 发版流水线（bump/Tag/CI-CD）← M3                          │
└──────────────────────────────────────────────────────────────┘
```

**核心判断**：Forge 的价值不在「一个生成器」，而在**为下游一切操作提供规范、可预测的目录契约**。把它作为 PM 的入口，能让「项目→组件→仓库→发版」从第一天起就建立在稳定结构上；反之做成并列工具，会形成两套入口、两套目录范式，与 PM「统一编排」的定位冲突。

### 3.2 解决方案结构与依赖

沿用评审报告 4.1 推荐的骨架，并按本能力补齐职责：

```text
Project_Manager/
├── ProjectManager.sln
├── src/
│   ├── ProjectManager.Scaffolding/  # 脚手架引擎（独立库，零 UI / 零 Storage 依赖）
│   │   ├── Models/                  # Template / ModuleOption / GenerationRequest / Result
│   │   ├── Templates/               # TemplateLoader（JSON→Template，含 schema 校验）
│   │   ├── Validation/              # ProjectValidator（名称/简介/路径）
│   │   ├── Naming/                  # 命名派生（pascal / kebab / snake）
│   │   └── Scaffolding/             # TreeBuilder / ScaffoldGenerator / Documents / Journal
│   ├── ProjectManager.App/          # WPF 表现层：主壳 + 新建项目向导 + 主题
│   ├── ProjectManager.Storage/      # SQLite + DPAPI：项目清单/最近项目/模板元数据
│   └── ProjectManager.CliInterop/   # Git CLI / gh / act 进程封装（git init 在此）
├── tests/
│   ├── ProjectManager.Scaffolding.Tests/   # 引擎单测（快照/幂等/回滚/边界）
│   └── fixtures/
│       └── forge-baseline/          # 冻结的 Forge 等价基线（见 9.1）
└── config/
    └── templates.json               # 随包分发的只读默认模板（可被用户目录覆盖）
```

> **为何引擎独立成项目**：① 强制"零 UI / 零 Storage 依赖"由项目边界保证，而非靠自觉；② 单测项目可只引用引擎，测试启动快、无 WPF 依赖；③ 未来若要提供命令行入口，只需薄壳引用，不会被迫拖入 Git/发版等领域依赖（本期不交付 CLI，见 8.2 D4）。

**依赖方向**：`App → Scaffolding / Storage / CliInterop`；`Scaffolding` 只依赖 BCL，保证可单测；`Storage` 不缓存 Git 实时状态；`CliInterop` 统一进程封装（超时看门狗、输出流式消费）。

### 3.3 Forge 模块 → PM 项目 映射表

| Project_Forge（Python） | Project_Manager（.NET） | 迁移要点 |
|---|---|---|
| `src/templates.py` | `Scaffolding/Templates/TemplateLoader.cs` | JSON→`Template`；校验规则逐条等价（结构非空、descriptions 非空、quickstart 非空、模块 key 唯一、路径段合法），并新增 `$schemaVersion` 校验 |
| `src/validation.py` | `Scaffolding/Validation/ProjectValidator.cs` | 名称/简介/路径三规则等价，错误文案沿用，另出 `ErrorCode` |
| `generator.build_structure` | `Scaffolding/TreeBuilder.cs` | 目录树展开 + 扁平化 + 空叶子收集 |
| `generator.generate` | `Scaffolding/ScaffoldGenerator.cs` | 预检 / 落盘 / 备份 / 占位 / 回滚五段式，加 journal |
| `generator.readme/structure/gitignore` | `Scaffolding/Documents.cs` | 文本产物，逐字等价（由冻结快照比对） |
| —（Forge 无此能力） | `Scaffolding/FileInjector.cs` | 新增 `files` 内容注入（P1-1） |
| —（Forge 无此能力） | `Scaffolding/Naming/NameDeriver.cs` | 新增命名派生（P1-3） |
| `src/app.py` | `App/Views/NewProjectWindow.xaml(+VM)` | 单页表单 → 三步向导（见第 6 节） |
| `src/main.py` | `App/App.xaml.cs` | 启动、模板加载失败的兜底提示 |
| `config/templates.json` | 用户目录 `%APPDATA%` / 安装目录 `config/` / 内置资源 | **三源优先级**（见 4.2），不再是"外置覆盖内置"的二元模型 |

### 3.4 与 PM 领域模型的打通

- **项目注册（P0-4）**：生成成功后自动把 `{id, name, path, template, template_hash, created_at, git_initialized}` 写入 `projects` 表，主壳「项目」列表即时可见。**注册是生成的组成部分，不是可选动作**——结果页因此不再提供「加入项目清单」按钮（见 6.4 结果页）。
- **生成元数据（P1-2）**：在项目根写入 `.pm-scaffold.json`（模板名 / `templateHash` / 模块集合 / 时间 / 应用版本）。用途：① 主壳识别"PM 生成"并显示徽标；② 模板升级后做"只加不删"的结构补充；③ 迁移统计。该文件**应提交进仓库**，不写入 `.gitignore`。
- **组件候选（P1-4）**：由模板显式声明 `components: ["apps","packages","contracts"]` 白名单决定，**不再"顶层目录天然即组件"**——否则 `docs/`、`assets/`、`config/`、`output/` 会被误判。白名单缺省为空，表示该模板的项目不参与组件识别（单体桌面工具即属此类）。
- **仓库清单**：若勾选「生成后初始化 Git」，`git init` 成功后把该目录加入仓库清单，供后续 Git 工作台使用。
- **发版复用**：生成的 `apps/*` 可作为多组件 bump 的对象；模板可声明 `release.tagPrefix`（扩展字段，见 4.2），供发版流水线使用。
- **最近项目**：主壳「最近生成」= `projects` 表按 `created_at` 倒序的一个视图，与 Forge 的「生成后打开目录」体验衔接。

### 3.5 分层职责与边界

| 层 | 职责 | 明确不做 |
|---|---|---|
| App | 向导编排、表单校验呈现、预览、结果/异常态、主题 | 不直接拼路径、不直接写文件 |
| Scaffolding（引擎库） | 模板解析、命名派生、树展开、生成、文件注入、文档产物、校验规则、journal 与回滚 | 不依赖 WPF、不访问数据库、不感知"项目清单"概念 |
| Storage | 项目/最近项目/模板元数据、设置、凭据引用 | **不缓存 Git 实时状态** |
| CliInterop | `git init`、后续 `gh`/`act` 进程封装 | 不承载业务规则 |

> **宿主数量（D4）**：本期只有 **App 一个宿主**。引擎独立成库是为边界与可测性，不是为将来并行发行第二个产品；若未来需要命令行入口，也只能作为 PM 的一个子命令发布，不得以 Forge 名义独立发行。

## 4. 功能整合与优化

### 4.1 入口与端到端流程

```text
主壳「新建项目」(Ctrl+N)
      │
      ▼
Step 1 基本信息 ──► Step 2 模板与模块 ──► Step 3 预览与确认
      │                                        │
      │                                        ▼
      │                              生成（Scaffolding，异步）
      │                                        │
      │                    ┌───────────────────┴───────────────────┐
      │                    ▼                                       ▼
      │              成功：结果页                          失败：原因 + 回滚说明
      │    （已在项目清单中 / 在项目中打开 / 复制路径）      （重试 / 修改路径 / 关闭）
      ▼
（取消：确认是否放弃已填内容；不落盘）
```

向导以**独立模态窗口**承载（决议 D1，规格见 6.4.0），三步导航在窗口内完成，主壳不被替换。与 Forge 单页表单相比，改为**向导式**：把「填什么」「选什么」「生成什么」拆成三步，降低单屏决策量，并在生成前给出**可预览的目录树与三类清单**（将创建 / 将备份 / 将保留），把 Forge 的「生成后才知道结果」前移为「生成前可确认」。

### 4.2 模板系统

**兼容性**：`templates.json` 与 Forge 完全兼容，字段保持不变：

```json
{
  "模板名": {
    "structure": { "顶层目录": ["相对子路径", "..."] },
    "modules": [{ "key": "web", "label": "Web 前端", "paths": ["apps/web", "output/web-dist"] }],
    "descriptions": { "相对路径": "中文说明" },
    "readme_quickstart": "快速开始文本",
    "gitignore": ["output/", "node_modules/"]
  }
}
```

**扩展字段**（全部可选，向后兼容；旧模板不填即用默认）：

| 字段 | 类型 | 用途 | 来源 |
|---|---|---|---|
| `displayName` | string | 展示名（默认取 key） | v1.1 |
| `description` | string | 模板一句话说明（Step 1 卡片用） | v1.1 |
| `icon` | string | 图标（内置或相对路径） | v1.1 |
| `release.tagPrefix` | string | 发版 Tag 前缀，供流水线复用 | v1.1 |
| `minAppVersion` | string | 模板要求的最低 PM 版本 | v1.1 |
| `files` | object | `落盘相对路径 → 模板内相对路径`，内容注入（P1-1） | v1.2 |
| `naming` | object | 命名派生风格：`namespaceCase` / `packageCase` / `dirCase`（P1-3） | v1.2 |
| `components` | string[] | 组件候选白名单，缺省为空 = 不参与组件识别（P1-4） | v1.2 |
| `$schemaVersion` | number | **顶层元键**（不在模板对象内），当前为 `1`（P1-5） | v1.2 |

> `$schemaVersion` 以 `$` 前缀置于 `templates.json` 顶层，加载器将其视为元数据而非模板名；缺失按 `1` 处理。加载到**更高版本**时只读降级并提示，未知字段不静默忽略而是记入警告列表。

**来源优先级（P0-2，v1.2 修正）**：原方案"`exe 旁 config` 热覆盖 → 内置资源"在真实安装形态下会失效——PM 经 Velopack 安装到 `C:\Program Files\...` 后该目录**标准用户不可写**，且更新会整体替换 app 目录，用户放的模板会被静默冲掉。改为三源：

| 优先级 | 位置 | 性质 | 用途 |
|---|---|---|---|
| 1 | `%APPDATA%\ProjectManager\templates.json` | 用户级、可写、跨版本存活 | 个人 / 团队热覆盖（主用） |
| 2 | 安装目录 `config/templates.json` | 只读、随包分发 | IT 统一部署的默认模板集 |
| 3 | 内置资源（程序集嵌入） | 只读、随二进制 | 离线兜底 |

**首次启动**：若用户目录无文件而安装目录有，则**复制**一份到用户目录（复制而非引用，避免更新覆盖与权限问题）。三者均做 schema 校验，失败时给出**可定位的错误**（模板名 + 字段 + 原因 + 错误码）。

**内置模板（决议②：3 套）**：保留「全栈项目」「轻量工具」，**新增「单体桌面工具」**（对齐 PM 自身形态：`src/`、`tests/`、`docs/`、`scripts/`、`config/`、`assets/`、`output/`）。三套模板的 `displayName` 均不超过 5 字，保证 Step 1 三张卡片等宽排布不折行；「单体桌面工具」完整定义见 5.1.1。

### 4.3 生成引擎不变量（必须保持，逐条验收）

| # | 不变量 | 说明 |
|---|---|---|
| G0 | **等价基线（P0-1）** | 行为等价以**冻结快照**（`tests/fixtures/forge-baseline/`）为唯一判定依据；快照必须在 Forge 归档前生成并入库（见 9.1） |
| G1 | **幂等** | 重跑不破坏已有内容；`README.md`/`structure.md` 同名先备份 `.{yyyyMMdd-HHmmss}.bak`；**同一秒内二次备份自动加序号**（`.bak-1`、`.bak-2`），不覆盖既有备份 |
| G2 | **保留 .gitignore** | 目标已存在 `.gitignore` 时保留原文件，不覆盖 |
| G3 | **占位规则** | 空叶子目录写 `.gitkeep`；被 `.gitignore` 忽略的目录跳过占位；**`.gitkeep` 已存在则跳过不重写**（不清空用户可能写入的内容） |
| G4 | **预检** | 父目录存在且可写；任一计划目录位置被同名文件占用则整体拒绝，并指出**首个冲突路径** |
| G5 | **回滚** | 失败时删除本次新建的空目录与占位文件；**不动用户既有文件** |
| G6 | **编码** | 统一 UTF-8 无 BOM；路径分隔内部统一 `/`，落盘用系统分隔符 |
| G7 | **纯逻辑** | 生成引擎不依赖 UI/数据库，可在无界面环境单测 |
| G8 | **回滚不可中断（P0-3）** | 回滚是**不可取消的临界区**：一旦进入，UI 禁用取消与关闭直至结束；取消请求只在"预检→建目录→写文件→占位"的**阶段间隙**生效 |
| G9 | **文件注入不动用户文件（P1-1）** | `files` 目标已存在 → 跳过并计入"将保留"；绝不覆盖用户已有文件 |
| G10 | **元数据可追溯（P1-2）** | 每次生成在项目根写 `.pm-scaffold.json`（模板名 / hash / 模块 / 时间 / 版本），供归属识别与增量同步 |

> **G0–G10 是「行为等价 + 安全边界」的判定基线**：G0–G7 对应 Forge 原有语义，G8–G10 为 PM 新增约束。测试用例与快照结构见 7.2 与 9.1。

### 4.4 增量能力（相对 Forge）

1. **生成后 `git init`**（可选勾选）：走 `CliInterop`，成功后把目录纳入仓库清单；失败不影响项目生成，仅在结果页提示。
2. **生成前预览**：实时目录树 + 三类清单（将创建 N 目录 / M 文件，将备份 k 个同名文件，将保留 .gitignore 与既有文件）。
3. **模板内容注入（P1-1）**：`files` 声明"落盘路径 → 模板内文件"，支持 4 个占位符 `{{name}} / {{description}} / {{date}} / {{template}}`，把"空目录骨架"升级为"可编译骨架"。
4. **命名派生（P1-3）**：Step 2 展示由项目名派生的目录名、根命名空间、包名、Tag 前缀，消除"生成后手工改名"。
5. **生成元数据（P1-2）**：落 `.pm-scaffold.json`，支撑归属识别与模板升级后的增量补结构。
6. **项目即时注册（P0-4）**：生成即入库，主壳「项目」与「最近」列表立即出现，无需二次导入。
7. **自定义模板校验**：导入/编辑 `templates.json` 时即时校验，错误定位到「模板名 + 字段 + 错误码」。
8. **复制路径 / 打开目录 / 定位文件**：结果页一键操作。

### 4.5 异常与边界（10 类，含错误码）

| 异常 | 错误码 | 触发 | UI 表现 | 处理 |
|---|---|---|---|---|
| 路径不存在 | `PM-SCF-001` | 父目录被删/盘符不存在 | 路径框下方错误 + 生成禁用 | 重新选择目录 |
| 路径不可写 | `PM-SCF-002` | 权限 / 只读介质 / `Program Files` | 路径框下方错误 + 生成禁用 | 提示换目录或提权 |
| 同名文件占用 | `PM-SCF-003` | 计划目录位置是文件 | 预检拦截，指出**首个冲突路径** | 换名或清理后重试 |
| 目标目录已存在 | `PM-SCF-004` | 项目目录已存在 | 生成前二次确认，展示三档策略（见下） | 合并 / 仅预览 / 取消 |
| 模板非法 | `PM-SCF-010` | JSON 语法 / 字段缺失 / 非法目录段 / 版本过高 | 启动或导入时错误面板 | 定位「模板名 + 字段」；回退下一优先级来源 |
| 模板过大 | `PM-SCF-011` | 超目录/文件/体积上限 | 导入时拒绝 | 提示具体超限项与上限 |
| 生成中断 | `PM-SCF-020` | 磁盘满 / IO 异常 / 进程被杀 | 结果页失败态 + 回滚说明 | 已回滚；可重试 |
| 回滚失败 | `PM-SCF-021` | 清理时文件被占 / 权限变化 | 失败态**升级为警告态** + 清单下载 | 输出「本次新增清单.txt」供手工清理 |
| 用户取消 | `PM-SCF-030` | 生成中取消 | 回到 Step 3，提示已回滚 | 可改参数重试 |
| 长路径/中文路径 | `PM-SCF-040` | >260 或特殊字符 | 输入即时提示 | 缩短路径；启用长路径策略（见 4.6） |

**目标目录已存在的三档策略（P0-3 配套，替代原"合并/覆盖"的模糊表述）**

| 档位 | 行为 | 适用 |
|---|---|---|
| **合并**（默认） | 只补缺失的目录与文件；同名文本走 `.bak` 备份后覆盖；`.gitignore` 与 `files` 目标**保留不动** | 老项目补结构 |
| **仅预览（dry-run）** | 只产出变更清单与目录树，不写任何字节 | 先看后决定；可导出清单 |
| **取消** | 不落盘 | — |

> 三档的"合并"必须与 G5/G9 一致：**永远不删除用户既有文件**。

> 错误码前缀 `PM-SCF`（Scaffolding），码与文案分离：UI 按码分支（可否重试 / 是否需提权 / 是否需换路径），日志按码聚合，支持按码定位。

### 4.6 非功能设计

- **长路径**：检测目标路径长度，超过 260 时提示；应用清单启用 `longPathAware`，内部路径操作使用 `\\?\` 前缀兜底。
- **中文路径**：全程 UTF-8；进程参数/环境变量使用宽字符 API，避免 ANSI 代码页问题。
- **OneDrive/占位文件**：预检时对「云端占位」文件按普通文件处理，避免误判为可覆盖目录。
- **路径形态边界**：UNC 路径（`\\server\share`）**支持但降级**（不启用长路径前缀，超长则拒绝）；符号链接 / junction 目标**拒绝生成**并提示（避免越界写入）；`.git` 目录**禁止作为生成位置**。
- **性能预算与护栏（P2-2，可验收）**：

| 项 | 预算 | 护栏上限 |
|---|---|---|
| 模板解析（3 套全量） | < 50 ms | 单模板 ≤ 5000 文件声明 |
| 树展开 1000 节点 | < 20 ms | 单模板 ≤ 2000 目录 |
| 落盘 500 目录（SSD） | < 800 ms | 总文本 ≤ 5 MB；单文件 ≤ 256 KB |
| 预览树首屏 | < 100 ms | 超过 500 节点启用虚拟化 |

  > 超限**不静默截断**，明确拒绝并提示具体超限项与上限（`PM-SCF-011`）。落盘在后台线程执行，UI 显示进度环与阶段文案（预检 / 建目录 / 写文件 / 占位）。
- **日志**：生成日志记录操作与结果，**默认脱敏绝对路径**（仅保留项目名与末级目录），符合数据最小化。
- **单实例**：多实例启动时聚焦已有窗口，避免并发写同一目录。

## 6. UI 设计与优化

### 6.1 设计原则

1. **与主壳同源**：Fluent（WPF-UI）、深浅色自适应、圆角与间距统一。
2. **渐进披露**：三步向导，每步只回答一个问题。
3. **可预览、可反悔**：生成前看到将发生什么；取消不落盘。
4. **即时校验**：输入即反馈，错误就近显示，底部汇总。
5. **键盘可达**：全流程可纯键盘完成，焦点顺序合理。

### 6.4 新建项目向导（核心，三步）

#### 6.4.0 窗口形态（决议①：独立 Window）

向导为**独立 `FluentWindow`**，不使用 `ContentDialog`。理由：三步导航需要稳定的尺寸与状态保持；Step 3 预览需要横向空间；遮罩式 Dialog 在长表单下易出现内容裁切与焦点困局。

| 属性 | 规格 | 说明 |
|---|---|---|
| 窗口类型 | `FluentWindow`（WPF-UI）/ 回退普通 `Window` | 与主壳共用主题资源字典 |
| 所有者 | `Owner = MainWindow`，`WindowStartupLocation = CenterOwner` | **模态**打开，主壳不可交互 |
| 任务栏 | `ShowInTaskbar = false` | 作为主壳的子任务呈现 |
| 初始尺寸 | `880 × 620`（Min `760 × 560`） | Step 3 展开预览区时按 `SizeToContent` 平滑过渡到 `980 × 700` |
| 缩放 | `CanResize`，可最大化 | 预览树与模块区随宽度自适应（`WrapPanel` / 星列） |
| 标题栏 | 自定义 `TitleBar`：标题「新建项目」+ 右侧 `×` | 标题区高 40px |
| 步骤条 | 标题区下方独立 48px 区域 | 三步：基本信息 / 模板与模块 / 预览与确认 |
| 内容区 | `MinHeight 360`，纵向 `ScrollViewer` | 步间切换不跳动；`MinHeight` 锁底 |
| 底部操作栏 | 高 56px，右对齐 | `[取消] [上一步] [下一步/生成]`；`取消` 常驻最左 |
| 状态 | 单 `ViewModel` 贯穿三步 | 后退不丢数据；关闭即丢弃（除已生成成功） |
| 单实例 | 同刻仅一个向导 | 生成中再次 `Ctrl+N` → 聚焦现有向导并 `SnackBar` 提示 |
| 关闭拦截 | 已填内容非空 | 弹「放弃本次填写？」二次确认 |
| 生成中 | 表单与导航禁用、进度环 + 阶段文案（预检/建目录/写文件/占位）；`Esc` 转为「取消生成」 | 取消请求**只在阶段间隙生效**（P0-3） |
| 回滚中 | 显示「正在清理…」，**取消与关闭均禁用** | 回滚是不可取消临界区（G8）；这是唯一允许阻塞关闭的场景 |
| 成功关闭 | 「完成」或 `×` 均关闭并回到主壳项目列表 | 新项目在列表顶部高亮 2s |

> **与主壳的边界**：向导只负责采集与呈现，所有落盘、校验规则、备份/回滚均调用 `Scaffolding` 引擎；向导关闭不留下任何后台任务（`CancellationToken` 随窗口销毁一并取消，但**已进入回滚阶段则必须执行完**）。

### 6.5 组件与状态规格

**输入框（TextBox）**

| 状态 | 边框 | 辅助文案 | 说明 |
|---|---|---|---|
| 默认 | `BorderBrush` | 占位符 | — |
| 聚焦 | `AccentBrush` 2px | — | 焦点环 |
| 错误 | `ErrorBrush` 2px | 红色错误文案（就近） | 失焦与输入均校验 |
| 禁用 | 降透明度 | — | 生成中 |

**模板卡片**

| 状态 | 表现 |
|---|---|
| 选中 | `AccentBrush` 边框 + 勾选角标 |
| 未选 | 常规边框，悬停加深 |
| 含模块 | 右下角显示「N 个模块」 |

**模块复选**：默认全选；支持全选/反选；无模块的模板显示灰字「该模板无需配置模块」。

**目录预览树（TreeView）**

| 节点类型 | 视觉 | **文字标签（必备）** | 读屏文案 |
|---|---|---|---|
| 将创建 | 常规前景 | `新增` | 将新建 |
| 将备份 | 琥珀色 + `↺` | `将备份` | 同名文件将被备份后覆盖 |
| 将保留 | 次要前景 | `保留` | 已存在，不覆盖 |
| 被忽略 | 次要前景、降透明度 | `已忽略` | 被 .gitignore 忽略，不占位 |

> **无障碍约束（P2-3）**：状态**不得只靠颜色或图标**表达——每个节点必须带文字标签（`↺` 仅是辅助）。这也是把原设计"琥珀色 + `↺`"补成"琥珀色 + `↺` + `将备份`"的原因。

**派生标识**：等宽字体、只读、可逐项复制；样式为 `label`（次要前景）+ 值（主要前景），四行等宽对齐。

**按钮**：主（Primary，`AccentBrush`）/ 次（Surface + 边框）/ 危险（Error）/ 加载（ProgressRing + 禁用）。

**通知**：成功用 `InfoBar`（Success），失败用 `InfoBar`（Error），避免仅靠弹窗。

### 6.6 交互与键盘/无障碍

- **快捷键**：`Ctrl+N` 新建；`Enter` 下一步/生成；`Esc` 关闭向导；`Tab/Shift+Tab` 顺序遍历；`Alt+1/2/3` 跳步。
- **即时校验**：输入时轻量校验，失焦时完整校验，底部汇总「有 N 处需要修正」并聚焦首个错误。
- **取消确认**：已填内容非空时，取消弹出「放弃本次填写？」。
- **生成中**：禁用表单与导航，显示进度环 + 阶段文案（预检 / 建目录 / 写文件 / 占位）；`Esc` 触发「取消生成」，取消**只在阶段间隙生效**。
- **回滚中**：显示「正在清理…」，取消与关闭均禁用（G8）；结束后回到 Step 3 并提示「已回滚，未留下半成品」。
- **无障碍**：所有控件有 `AutomationProperties.Name`；错误文案与输入控件 `LabeledBy` 关联；预览树状态带文字标签（不只靠颜色）；对比度满足 WCAG AA。
- **DPI**：125% / 150% / 200% 下布局不重叠；最小窗口 `760×560` 时模板卡片由 3 列坍缩为单列纵向，预览树与模块区改为可折叠面板。
- **主题**：切换即时生效，向导与主壳共用主题资源。

### 6.10 文案规范

- 标题：动词/名词短语，如「新建项目」「预览与确认」。
- 主按钮：动作明确，如「生成」「下一步」「打开目录」。
- 错误：**现象 + 原因 + 建议**，如「生成路径不可写：D:\Projects。请选择有写权限的目录，或以管理员身份运行。」
- 成功：**结果 + 位置 + 后续动作**，如「生成成功。位置：D:\Projects\MyProject。已在项目清单中，可打开目录或在项目中打开。」
- 错误码：以小号次要前景附在标题右侧（如 `PM-SCF-002`），**不进入主句**；主句始终是"现象 + 原因 + 建议"，保证普通用户可读、支持人员可定位。
- 避免术语堆砌；面向用户用「目录」而非「节点」，用「模板」而非「schema」。

### 8.3 Forge 下线与迁移（因 D3「不保留」）

**替代硬门槛（缺一不可，全部达成才允许对外宣布替代）**

1. **G0 快照已冻结入库**（`tests/fixtures/forge-baseline/`，8 组用例），且可在干净环境中复现；
2. 第 4.3 节 **G1–G10 全部单测通过**（含 G8 回滚中断保护、G9 文件注入不覆盖、G10 元数据完整）；
3. 三套模板（全栈项目、轻量工具、单体桌面工具）在 PM 中生成结果与快照等价，README/structure/gitignore **逐字一致**；
4. M2 出口达成（生成后主壳可见、可打开、可登记），且内部自用 ≥5 个工作日无阻断缺陷。

> 关键变化（v1.2）：判定依据从"与 Forge 直接比对"改为"**与冻结快照比对**"。原因见 P0-1——Forge 归档后原始产物不可再生，快照是唯一可复查的基线。

**迁移步骤（用户侧成本目标：0 步）**

| 步骤 | 动作 | 说明 |
|---|---|---|
| **0** | **冻结等价基线（P0-1，前置且不可逆）** | 在 Forge 仍可运行时跑出 8 组用例产物，固化为 `tree.json`（路径 + SHA256 + 占位/忽略标记）与 `files/`（逐字内容）入库 |
| 1 | 模板配置迁移 | `templates.json` **字段兼容**，直接复制到用户目录或安装目录的 `config/`；含非法目录段时按 4.2 定位到「模板名 + 字段 + 错误码」并提示修正 |
| 2 | 既有项目迁移 | **无需迁移**——Forge 只写文件、无自有状态库；已生成的项目在 PM 中「打开已有项目」即可接管，并可按需补写 `.pm-scaffold.json` |
| 3 | Forge 收口 | README 顶部加 `DEPRECATED` 指向 PM；打最后一版 tag；仓库置归档只读，**不删除源码** |
| 4 | 回归比对能力 | PM 侧内部保留快照比对工具（仅测试用、不暴露 UI 入口），用于后续回归；不保留"调用 Forge"的兼容模式（D4：不引入 Python 运行时依赖） |

**无并行期的风险与对策**

| 风险 | 对策 |
|---|---|
| PM 出现阻断缺陷时用户无回退入口 | ① 严格执行上述硬门槛；② 保留 Forge 最后一版的安装包与源码 tag（归档 ≠ 删除），必要时由支持渠道临时提供；③ PM 首版把「模板导入 + 生成」做成**可独立交付的完整路径**，不依赖 Git 工作台/发版模块即可用 |
| 用户习惯的「单页表单」被三步向导替代，学习成本 | Step 1 一屏即可完成名称/简介/路径/模板；`Alt+1/2/3` 跳步；`Enter` 连续下一步——最快 3 次回车完成 |
| 老模板缺少新增扩展字段（`displayName`/`release`） | 全部可选，缺省取 `key`，行为不降级 |

## 9. 附录 A：等价基线与核对表

### 9.1 等价基线：冻结快照（P0-1）

**为什么必须快照**：D3/D4 决定不保留 Forge。一旦归档，"与 Forge 逐字等价"就失去可执行依据——而 R3 恰恰把这条当成替代硬门槛。因此必须在归档前把 Forge 的输出**冻结成资产**。

**用例矩阵（8 组）**

| # | 模板 | 模块 | 目标目录初态 | 验证目标 |
|---|---|---|---|---|
| 1 | 全栈项目 | 全勾选 | 空目录 | 完整结构 |
| 2 | 全栈项目 | 全部不勾 | 空目录 | 退化 + `.gitkeep` |
| 3 | 轻量工具 | 无模块 | 空目录 | 基线 |
| 4 | 轻量工具 | 无模块 | 空目录 | 基线（重复校验稳定性） |
| 5 | 单体桌面工具 | 全勾选 | 空目录 | 新模板完整结构 |
| 6 | 单体桌面工具 | 仅主模块 | 空目录 | `.gitkeep` 退化路径 |
| 7 | 全栈项目 | 全勾选 | **已有 README + .gitignore** | G1 幂等 / G2 保留 |
| 8 | 单体桌面工具 | 全勾选 | **已有 README** | G1 幂等（新模板） |

> 第 3、4 组内容相同但分两次跑，用于确认产物**确定性**（无时间戳污染的内容必须完全一致；含时间戳的文件在快照中做占位化处理）。

**固件结构**

```text
tests/fixtures/forge-baseline/
├── case-01-fullstack-all/
│   ├── tree.json          # [{ path, type, sha256, isPlaceholder, ignored }]
│   └── files/             # 逐字内容，便于人眼 diff
├── case-02-fullstack-none/
├── ...
└── CASE-MATRIX.md         # 用例说明与生成方式
```

**快照生成规则**：`tree.json` 中的 `sha256` 对文本内容计算；`.bak` 文件名中的时间戳、`{{date}}` 替换结果等**易变内容做占位化**（替换为 `<TIMESTAMP>` / `<DATE>` 后再计算 hash），否则快照永远不稳定。

### 9.2 核对表（语义索引）

> 本表用于**人读与评审**，不作为自动判定依据；自动判定以 9.1 快照比对为准。

| Forge 行为 | 融合后落点 | 等价要求 |
|---|---|---|
| 名称 ≤50、禁非法字符、保留名、不以点结尾 | `ProjectValidator.ValidateName` | 逐条一致，文案一致 |
| 简介非空、≤200 | `ProjectValidator.ValidateDescription` | 一致 |
| 路径存在且可写 | `ProjectValidator.ValidateTargetDir` + 预检 | 一致，错误可定位 |
| 结构展开 + 模块合并 | `TreeBuilder.ExpandStructure` | 一致（含顺序语义） |
| 预检（父目录/同名文件） | `ScaffoldGenerator.Preflight` | 一致 |
| 落盘与 `.bak` 备份 | `ScaffoldGenerator.WriteText` | 备份命名 `{name}.{时间戳}.bak` |
| `.gitignore` 保留 | `WriteGitignore` | 已存在则保留 |
| `.gitkeep` 占位（跳过忽略目录） | `WritePlaceholders` | 一致 |
| 失败回滚 | `Rollback` + `RemovePlaceholders` | 一致，不动用户文件 |
| README/structure/gitignore 文本 | `Documents` | 逐字一致 |
| 模板 JSON 结构与校验 | `TemplateLoader` | 字段与校验一致 |
| 深浅色 | `ThemeManager` + WPF-UI | 一致并可切换 |
