## 1. P0：不补会有返工或不可逆损失

### P0-1 等价基线必须在 Forge 归档前冻结为快照

**问题**：D3 决议"不保留 Forge 独立版"，R3 把"第 9 节等价核对全过"设为替代硬门槛。但第 9 节是一张**人工核对表**——Forge 归档后，"逐字等价"这句话没有任何可执行的判定依据，门槛变成不可复查的口头承诺。

**建议**：在归档动作**之前**（也就是现在），用 Forge 现有实现跑出一组基准产物，作为测试固件入库：

- **用例矩阵**：3 套模板 × {全模块勾选, 仅顶层} = 6 组；再加 2 组"预置 `README.md` + `.gitignore` 后重跑"（专门锁 G1 幂等与 G2 保留）。
- **固件内容**：
  - `tests/fixtures/forge-baseline/<case>/tree.json` —— 相对路径 + 内容 SHA256 + 是否占位文件 + 是否被忽略
  - `tests/fixtures/forge-baseline/<case>/files/**` —— 逐字内容（便于人眼 diff，不只存 hash）
- **PM 侧**：单测直接快照比对；差异输出"新增/缺失/内容不一致"三类，便于定位。

**为什么是 P0**：这是唯一**过期不可补**的动作。Forge 一旦归档或环境变化（Python 版本、路径），基准就再也做不出来了。

**落点**：7.2 验收清单改为"快照比对"；第 9 节加一句"本轮起以快照为基线，核对表仅作语义索引"；8.3 增加"迁移步骤 0：冻结基线"。

---

### P0-2 模板来源优先级踩了"安装目录只读"的坑

**问题**：4.2 现写"`exe 旁 config/templates.json`（热覆盖）→ 内置默认资源"。两个现实问题：

1. PM 经 Velopack 安装到 `C:\Program Files\...` 后，该目录**标准用户不可写** → 文档主打的"模板热覆盖"直接失效；
2. Velopack 更新会替换 app 目录 → 用户/IT 手工放进 `config/` 的模板**被更新冲掉**，且无提示。

**建议**：三源优先级重排，并区分"可写"与"随包分发"：

| 优先级 | 位置 | 性质 | 用途 |
|---|---|---|---|
| 1 | `%APPDATA%\ProjectManager\templates.json` | 用户级、可写、跨版本存活 | 团队/个人热覆盖 |
| 2 | 安装目录 `config/templates.json` | 只读、随包装 | IT 统一部署的默认模板集 |
| 3 | 内置资源 | 只读、随二进制 | 离线兜底 |

- 首次启动：若 APPDATA 无文件而安装目录有，则**复制**一份到 APPDATA（复制而非引用，避免更新影响与权限问题）。
- 5.3 设置项的"模板目录"改为"当前生效来源（只读展示）+ 打开所在文件夹"。

**落点**：4.2、5.3、5.4。

---

### P0-3 取消与回滚的原子性必须写死

**问题**：6.4.0 只写了"取消后由 Core 回滚未完成部分"，但三件事没定义：

1. 回滚过程中用户再点"取消"怎么办？
2. 回滚本身失败（磁盘满、文件被占、权限变化）怎么办？
3. 用户怎么知道哪些目录是本次新增的？

若回滚可被中断，就会留下**"半生成"目录**——比"生成失败"更糟：用户无法区分"模板产物"与"自己原有内容"，也不敢删。

**建议**：

- **回滚是不可取消的临界区**：UI 显示"正在清理…"，禁用关闭与取消直到结束（这是唯一允许阻塞关闭的场景）。
- **取消只在阶段间隙生效**：`预检 → 建目录 → 写文件 → 占位`，仅在阶段边界检查 `CancellationToken`，阶段内不中断（避免产生"半个文件"）。
- **journal 驱动**：Core 先记变更日志再执行；回滚 = 逆序撤销 journal。收益：可审计、可重放、可生成"本次新增清单"。
- **回滚失败的降级**：输出 `本次新增清单-<时间戳>.txt`（逐行路径），结果页明确"以下 N 项需手动删除（已为你列出清单）"，而不是静默失败。

**落点**：4.3 新增 **G8「回滚不可中断」**；4.5 失败行补"回滚失败"子态；6.4.0 关闭拦截段落补"回滚中禁止关闭"。

---

### P0-4 结果页"加入项目清单"与"生成即注册"自相矛盾

**问题**：3.4 与 4.4-5 明确"生成成功即注册为受管项目"，但 6.4 结果页仍给 `[加入项目清单]` 按钮，4.1 流程图同样。用户会理解为"注册是可选的、还没注册"。

**建议**：

- 默认态：文字状态 `已在项目清单中` + 主按钮 `[在项目中打开]`（跳转主壳项目详情）。
- 降级态（仅当主壳未就绪/注册失败）：`[重试注册]` + 说明"文件已生成，仅登记失败，不影响使用"。
- 同步修 4.1 流程图与 6.9 线框、6.10 文案示例。

**落点**：3.4、4.1、6.4、6.9、6.10。

---

### P0-5 里程碑切分有洞：M2 生成完的项目无处可见

**问题**：7.1 把"项目清单/最近列表"放在 M3，M2 只做向导 UI。结果：M2 验收时用户生成成功、关闭向导，主壳仍是空状态——**"生成即注册"这条核心不变量在 M2 根本无法验证**。

**建议**：按"用户可感知闭环"而非技术层切分：

| 里程碑 | 调整 |
|---|---|
| M2 | 向导 UI **+ 项目注册 + 最近项目列表（只读）** → 出口：生成后可在主壳看到并打开 |
| M3 | 组件识别 / 仓库清单 / `git init` / 项目详情页 → 出口：可编排与暂存 |

**落点**：7.1、7.2。

## 2. P1：价值高，建议纳入 M2

### P1-1 模板只能造空目录 —— 加最小 `files` 能力

**问题**：当前产物 = 若干空目录 + `README.md` / `structure.md` / `.gitignore`。用户拿到 `src/Core/` 后仍要手写 `.sln`、`.csproj`、`package.json`。"脚手架"的价值停在"目录约定"，没到"可编译"。

**建议**——刻意做小，避免长成模板引擎：

```json
{
  "单体桌面工具": {
    "files": {
      "src/Core/Core.csproj": "dotnet/classlib.csproj",
      "src/App/App.csproj": "dotnet/wpf.csproj",
      "ProjectManager.sln": "dotnet/solution.sln"
    }
  }
}
```

- 模板文件放 `templates/<模板名>/files/**`，`files` 仅做"落盘路径 → 模板内相对路径"映射。
- **只支持 4 个占位符**：`{{name}}`、`{{description}}`、`{{date}}`、`{{template}}`，不做条件、循环、继承。
- 目标已存在 → **跳过并计入"将保留"**（守住 G5：不动用户文件）。
- 不支持二进制；单文件 ≤256KB，总模板 ≤5MB。

**落点**：4.2（字段）、4.3（新增文件写入不变量）、5.1.1（给单体桌面模板补一组 `files`）。

---

### P1-2 项目内落地生成元数据，支持"归属识别"与"重新同步"

**问题**：没有元数据，PM 无法区分"自己生成的项目"与"外部打开的项目"，也无法在模板升级后做增量同步（只知道加，不知道上次加过什么）。

**建议**：生成成功时在项目根写 `.pm-scaffold.json`：

```json
{ "schemaVersion": 1, "template": "单体桌面工具", "templateHash": "sha256:…",
  "modules": ["desktop", "tests"], "createdAt": "2026-10-23T17:00:00+08:00", "appVersion": "1.0.0" }
```

- **应提交进仓库**（团队共享，支持协作方识别），不写入 `.gitignore`。
- 等价性快照比对时列入排除表（Forge 基线不含此文件）。
- 用途：① 主壳标识"PM 生成"徽标；② 模板升级后"只加不删"的补结构；③ 迁移统计。

**落点**：3.4、4.3、5.2。

---

### P1-3 命名派生没设计，生成完还得改名

**问题**：Step 1 只校验项目名。但由项目名派生的**目录名 / 根命名空间 / 包名 / Tag 前缀**没有规则，也没有呈现。一旦 P1-1 的 `files` 启用，模板里 `{{name}}` 到底替换成 `MyProject` 还是 `my-project` 会各写各的。

**建议**：Step 2 增"派生标识"只读区块（4 行，等宽字体）：目录名、根命名空间、包名、Tag 前缀；风格由模板声明：

```json
"naming": { "namespaceCase": "pascal", "packageCase": "kebab", "dirCase": "pascal" }
```

缺省 `pascal / kebab`；派生结果可复制（便于用户在别处粘贴）。

**落点**：4.2、6.4 Step 2、5.1.1。

---

### P1-4 组件候选需要白名单，否则 `docs/` 会被当作组件

**问题**：3.4 称"顶层目录天然是组件识别的输入"。但 `docs/`、`assets/`、`config/`、`output/` 显然是噪声，M3 组件识别会误报，用户还要手工排除。

**建议**：模板加**显式白名单**（比从 `descriptions` 猜语义可靠）：

```json
"components": ["apps", "packages", "contracts"]
```

缺省为空 = 该模板的项目不参与组件识别（单体桌面工具就属于这种）。

**落点**：4.2、3.4、5.1.1。

---

### P1-5 错误码与 schemaVersion：排障与演进的地基

**问题**：现在只有中文文案。而 UI 需要按错误类型分支（能否重试 / 是否需提权 / 是否需换路径）、日志需要聚合、支持需要定位——都缺机器可读标识。模板格式亦无版本号，加字段后无法判定兼容性。

**建议**：

- 定义 `PM-SCF-0xx` 错误码（约 12 条）：路径不存在/不可写/同名文件冲突/模板非法/回滚失败/用户取消/超限/编码失败…；`ErrorCode` 与文案分离，文案可本地化。
- `templates.json` 顶层加 `"schemaVersion": 1`；加载器遇到更高版本 → 只读降级并提示（不静默忽略未知字段）。

**落点**：4.5（表格加"错误码"列）、5.1。

## 3. P2：可选，后续里程碑

### P2-1 批量生成（一次建多个仓库）

多仓库场景常见"一次建 3 个服务"。建议 M3 之后加批量模式：一个父目录 + 多行项目名 + 共用模板，逐项生成并按结果汇总（部分成功必须能单独重试）。

> **前置依赖**：批量会把"部分失败"的复杂度放大一个量级，务必在 **P0-3 的 journal 机制**落地之后再做，否则回滚语义会失控。

**落点**：4.4、7.1（M3+）。

---

### P2-2 性能护栏与可验收预算

"毫秒级"不可验收。建议给出**预算 + 上限**：

| 项 | 预算 | 护栏 |
|---|---|---|
| 模板解析（3 套） | < 50ms | — |
| 树展开 1000 节点 | < 20ms | 单模板 ≤ 2000 目录 |
| 落盘 500 目录（SSD） | < 800ms | ≤ 5000 文件 / 总文本 ≤ 5MB |
| 预览树首屏 | < 100ms | 超过 500 节点改虚拟化 |

超限不静默截断，明确拒绝并提示"模板过大：N 个目录，上限 2000"。

**落点**：4.6。

---

### P2-3 实现层两条护栏

**a) WPF-UI 依赖隔离**
- 视图层不直接引第三方命名空间；WPF-UI 只出现在 `Themes/` 与薄封装（`PmButton`、`PmTextBox`、`PmCard`）。
- 远程桌面/虚拟机下 Mica 易出现黑块 → 检测（`SystemParameters`/RDP 会话）+ 设置项可关闭，降级为纯色背景。
- 收益：R1（API 变动返工）从"全视图返工"降为"只改封装层"。

**b) 无障碍与 DPI**
- 预览树"将备份"当前规格是"琥珀色 + `↺`"——**违反"不只靠颜色/图形"原则**，须补文字标签「将备份」。
- 补 DPI 125% / 150% / 200% 与最小窗口（760×560）的布局坍缩规则：三张模板卡片在窄宽度下改为单列纵向。

**落点**：6.5、6.7。

## 4. 明确"不做"（范围守卫）

| # | 不做 | 理由 |
|---|---|---|
| N1 | 模板市场 / 远程拉取 | 引入签名、版本、离线缓存、供应链信任，收益远小于成本；维持 M4 可选，本期不承诺 |
| N2 | 通用模板引擎（条件/循环/继承） | 一旦支持就是另一个产品；`files` + 4 占位符已覆盖 95% 场景 |
| N3 | 生成后自动 `restore` / 装依赖 | 网络与时长不可控，破坏"纯本地、秒级、离线可用"的核心体验；仅提示下一步命令 |

## 5. 如果只做三件事

1. **P0-1 快照基线** —— 唯一"过期不可补"的动作，也是 D3 决议成立的前提。
2. **P1-1 `files` 能力** —— 决定"脚手架"到底有没有用，而不只是建空壳。
3. **P0-2 模板来源优先级** —— 上线即失效的坑，修复成本极低。

## 7. 形态选型：Forge 该"单独软件引入"还是"整合进软件"（D3 边界复核）

**结论（已决议 D4，见正文 8.2）：整合进 PM，不作为独立软件引入。但要把"能力"与"宿主"分开——能力做成可复用引擎，宿主只保留 PM 主程序一个。**

### 7.1 三种形态对比

| 维度 | A · 独立软件并行（Forge 自成产品） | B · 完全整合进 PM（单一 GUI） | C · 一引擎 + 双宿主（推荐） |
|---|---|---|---|
| 主路径体验 | 建完关掉 → 开 PM → 导入（两跳） | `Ctrl+N` 生成即注册（一跳） | 同 B，另提供 CLI 出口 |
| 技术栈 | Python + .NET 两套 | 一套 .NET | 一套 .NET（CLI 复用同一引擎） |
| 需维护 | 2 套 UI/主题/打包/更新/日志/设置 | 1 套 | 1 套 + 一层薄 CLI |
| 生成即注册 | ✗ 只能靠文件系统约定 + 二次导入 | ✓ | ✓ |
| 组件识别衔接 | ✗ 跨进程无契约 | ✓ 模板 `components` 白名单直供 | ✓ |
| 轻量场景（不装 PM） | ✓ | ✗ | ✓ CLI 可单文件分发 |
| CI / 无图形环境 | ✗（Tkinter 需桌面） | ✗ | ✓ |
| 维护税 | **最高** | 最低 | 低 |

### 7.2 为什么"完全整合"仍不够——要留 CLI 出口

真实需求里有一类不该被忽视：只想生成一套目录骨架、不想装一个多仓库编排工具的人（新同事、外部协作方、脚本、CI）。若只有 GUI，这类需求会被迫装 PM 或用回 Python 版，从而把 D3 否决的东西又请回来。

CLI 的成本极低：`Core` 已按纯逻辑设计、零 UI 依赖，CLI 只是 `Program.cs` 里解析 `--template/--modules/--path/--json` 再调同一个入口，**不新增任何业务逻辑、不新增测试分支**（复用同一套快照基线）。

### 7.3 什么时候才该真做"独立软件"

满足其中两条以上才考虑，否则一律走 C：

1. 目标用户与 PM 用户**不是同一批人**（例如面向非开发者的通用脚手架）；
2. 需要**独立分发渠道**（应用商店、社区下载、单独版本节奏）；
3. 团队能长期供养第二套技术栈（UI + 打包 + 更新 + 主题 + 日志）；
4. 生成能力需要与 PM 的领域数据**完全解耦**（当前恰恰相反：生成即注册、组件候选、仓库清单都依赖 PM）。

按现状看，第 4 条已明确不成立，第 1、2 条也不成立，因此不满足。

### 7.4 与决议 D3 的关系

D3 否决的是「**独立 GUI 并行发版**」，不否决「同一引擎的 CLI 出口」——两者是不同层次的决策，不冲突。建议把 D3 的表述补一句边界：

> 不保留 Forge 独立 GUI 发行版；允许以 `pmcli` 形式提供同一引擎的命令行出口（不单独维护业务逻辑与模板）。

若你认为"CLI 也算独立软件"，则需重新界定 D3 范围——请明确，我再调整方案与里程碑（CLI 从 M3 的可选增量变为 M2 的交付项）。

### 7.5 交付结构建议（落在 3.2 解决方案骨架）

```text
src/
├── ProjectManager.Scaffolding/   # 引擎：模板/校验/树/落盘/回滚（纯逻辑，零 UI）
├── ProjectManager.App/           # WPF 宿主：三步向导
├── ProjectManager.Cli/           # CLI 宿主：pmcli new（可选，M3）
├── ProjectManager.Storage/       # 项目清单/最近项目
└── ProjectManager.CliInterop/    # git init 等进程封装
```

> 注意：当前 3.2 把引擎放在 `Core` 内部。建议**独立成 `ProjectManager.Scaffolding` 项目**——这样 CLI 引用它时不会被迫拖入 Git/发版等领域依赖，也强制了"引擎零依赖"的边界。
