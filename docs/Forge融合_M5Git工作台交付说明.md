## 1. 为什么现在做这件事

先摆事实：M4 收尾时，PM 对 Git 仓库是**只读**的。

- 详情页能显示「main · 3 处未提交改动」；
- 仓库页能汇总所有项目的仓库状态；
- 侧栏挂着「历史」「发版」两个永久禁用项。

但用户看到「N 处未提交改动」之后，**没有任何去处**。这个数字是个死胡同——他知道有问题，却只能在 PM 之外打开终端或别的 Git 客户端。这不是"少个功能"，是**承诺了状态却不给动作**。

更要紧的是：这件事在计划里**根本没有工作包**。

> 《方案》§0.2 明确写着「不重复《软件设计方案 v2》已定稿的 Git 工作台细节，仅说明与本能力的衔接点」——于是《开发计划》M1–M4 全部 WP 里，没有任何一项对应 Git 工作台。这不是"暂时不做"，是**计划缺口**：侧栏那两个禁用项就是缺口的可见症状。

所以本轮先补计划（《开发计划》§6.5 新增 M5，G5 门禁），再补实现。按《开发计划》§11「新增需求 → 先判断属于哪个阶段」处理，而不是硬塞进 M4。

## 2. 交付内容

### 2.1 引擎侧：两个可单测的解析器

| 文件 | 职责 |
|---|---|
| `src/ProjectManager.CliInterop/GitChanges.cs` | `git status --porcelain=v2 -z` → `GitChangeEntry` |
| `src/ProjectManager.CliInterop/GitDiff.cs` | `git diff` → `FileDiff` / `DiffHunk` / `DiffLine` |

**为什么是 porcelain v2 + `-z`**：

- v1 的重命名输出是 `R  old -> new`，要把路径从箭头里"猜"出来——路径本身含 ` -> ` 时就解析错。v2 把源路径放在**独立字段**里，没有歧义。
- `-z` 下记录以 NUL 分隔且**不做路径转义**，含空格、中文、引号都不加引号。这是 Windows 中文路径上唯一稳定的组合。
- `--untracked-files=all` 不折叠未跟踪目录。工作台的用途就是"挑文件提交"，只给一个 `docs/` 等于让用户全提交或全不提交。

**为什么解析器是纯函数**：状态码规则很多（`XY` 两字符、type 1/2/u/? 四种记录、重命名源路径独立成段），能用字符串表覆盖的就不该起 git 进程去验。全部 13 项解析断言都不碰磁盘。

**三类容易错的地方，都在断言里钉住了**：

| 坑 | 处理 |
|---|---|
| type 2（重命名）比 type 1 多一个 `Xscore` 字段，路径下标从 8 变 9 | `Ordinary(token, pathIndex)` 显式传下标；重命名后跟一条未跟踪记录，验证不被源路径吞掉 |
| `HasStagedChanges` 把未跟踪算成"已暂存" | `Staged is not (Unmodified or Untracked)`。错的时候"可提交 N 项"在没执行过 `add` 时就是错的——注入验证时这一条让 2 项断言变红 |
| diff hunk 末尾的换行残留被当成"空的上下文行" | `IsSatisfied` 判定必须在空行分支**之前**。否则 `+3 −1` 变成 `+3 −1` 却多算一行上下文 |

**明确不支持的**（写进注释，避免被当成 bug）：

- 合并冲突的 `diff --cc` 段（`@@@` 三父格式）：冲突文件在 UI 上直接提示"需在外部解决"，比给一个三方 diff 的半成品更有用。
- 未跟踪文件的逐行 diff：`git diff` 不产出未跟踪内容，硬凑 `--no-index` 要在 Windows 上依赖 `NUL` 设备与退出码 1 的特殊语义，为一个预览功能引入平台差异不值得。

### 2.2 写操作：一律走 CLI

`src/ProjectManager.CliInterop/GitRunner.Workspace.cs` 是 `GitRunner` 的分部类，新增 `IGitWorkspaceRunner`：

```
GetWorkingTreeAsync / GetDiffAsync / StageAsync / UnstageAsync / CommitAsync
```

**四个刻意的设计**：

1. **提交走 Git CLI，不用 LibGit2Sharp**。《软件设计方案》§2.1 的红约束：LibGit2Sharp 的 commit 路径**不执行** `pre-commit` / `commit-msg` hook，用它会让仓库自己的规范静默失效。本项目本来就零 NuGet，但这条约束的意义不止于此——将来若引入 LibGit2Sharp 做 Hunk 暂存，提交仍然必须留在 CLI 侧。
2. **每仓库一把写锁**（`SemaphoreSlim(1,1)`，按仓库根归一化后分配）。两个 `git add` 同时跑会撞 `index.lock`。锁按仓库分配而非全局一把——全局锁会让多仓库操作互相排队。
3. **提交后回读**，不信任退出码。`git log -1 --format=%H%n%s` 拿实际 hash 与标题：hook 可以改写提交信息，把用户输入当结果显示是错的。
4. **hook 拒绝时原文透传**。`git commit` 失败时 git 把理由写在 stderr，替他改写成"提交失败"会丢掉唯一能让他知道该怎么改的信息。注入验证时把这条改成固定文案，1 项断言立刻变红。

**一个需要说明的兜底**：`UnstageArguments(bool hasHead)` 有 HEAD 时用 `git reset -q --`，零提交仓库退回 `git rm --cached -q -r --`（老版本 git 的 `reset` 会报 `Failed to resolve 'HEAD'`）。

> ⚠️ 实测 git 2.55 上 `reset -- path` 已经能处理无 HEAD 的情况，所以 `rm --cached` 这条**在当前环境走不到**。它不是"死代码"，但确实无法用集成测试证明——所以参数构造单独抽成 `public static` 纯函数，用 5 项断言钉住（`rm` / `--cached` / `-r` / `--` 分隔符）。第一次注入验证把它改回 `reset` 时**测试全绿**，才发现原来"零提交仓库取消暂存"那条集成断言根本区分不出两条路径。这件事记在这里，是为了说明：**没变红的注入验证，比失败的更值得记录**。

### 2.3 编排层：`GitWorkspaceService`

| 方法 | 集中了什么 |
|---|---|
| `LoadAsync` | 工作区快照 → `GitWorkspaceView` |
| `LoadDiffAsync` | 按"有暂存看索引区、否则看工作区"选 diff 源；未跟踪直接返回空 diff 并说明 |
| `SetStagedAsync` | 暂存/取消暂存 |
| `CommitAsync` | 校验 → 执行 → **回读**三段式 |
| `OrderForDisplay` | 纯函数排序：冲突 → 已暂存 → 未暂存 → 未跟踪，同类按路径序 |

**排序规则为什么要固定**：冲突排最前是因为它**阻塞提交**（有未解决冲突，git 直接不让 commit）。顺序必须稳定、不依赖 git 输出顺序，否则每次刷新列表都在跳，用户勾选会勾错行。

**提交前校验**：空标题 / 超 200 字 / 索引区为空，三条都在调 git **之前**返回。索引区为空时不靠 git 的 `nothing to commit`——那句话在中文环境下是本地化的、也可能被 hook 干扰，自己判更稳。

### 2.4 界面：侧栏第六项「变更」

见 `docs/Forge融合方案与UI设计.md` §6.3 补注（M5）。

```text
┌─ 变更   main · 3 个文件有改动（已暂存 1）              [刷新] ┐
├───────────────┬──────────────────────────────────────────┤
│ 勾选后可暂存   │ src/Util.cs                    修改 · +3 −1 │
│ ☐ Util.cs     │  2   2  @@ -2,5 +2,7 @@ namespace Demo;   │
│   已暂存·修改 │  3   3  public static class Util          │
│ ☑ App.cs      │  4   4  {                                 │
│   修改        │  5   -      Add(a,b) => a + b;            │
│ ☑ notes.md    │     6  +      Add(a,b) => checked(a+b);   │
│   未跟踪      │     7  +  ...Multiply...                   │
├───────────────┴──────────────────────────────────────────┤
│ 提交标题 [___________________]  [暂存所选][取消暂存][提交] │
│ 描述(可选)[__________________]                            │
└──────────────────────────────────────────────────────────┘
```

**三个刻意的取舍**：

1. **勾选 ≠ 立即写索引**。勾选只表示"我打算处理这个文件"，写索引是显式按钮动作。即时写索引是 GitHub Desktop 的做法，但那样每次误点都改仓库状态、失败还得回滚勾选——多一条能出错的路径，换不来更少的点击。
2. **默认勾选规则**：已有暂存内容的不预选，其余预选。用户打开工作台最常见的动作是"把这些都提交了"，所以默认勾上待处理的；已经暂存的不再预选，避免重复处理。
3. **diff 增绿删红**，不套用国内行情的红涨绿跌。这里表达的是"代码被加了/被删了"，不是价格方向；混用会让"删除"看起来像"上涨"。

**截图暴露并修掉的两个问题**：

- **Header 重复 `@@`**：`DiffRow` 的 Marker 写 `@@`，而 hunk header 文本自带 `@@ -1,3 +1,4 @@`，渲染成 `@@ @@ -1,3...`。改为 header 行 Marker 置空。
- **SnackBar 压住提交按钮**：提示浮在右下 `Margin 24`，正好盖住「提交」按钮的右半。改为在变更页抬高到 `152`（`DataTrigger` 绑定 `IsChangesSection`）。这是真实可用性问题：提交成功/失败时想再点一次，得等提示消失。

## 4. 已知限制（不是遗漏，是明确不做的）

| 限制 | 理由 | 归属 |
|---|---|---|
| 无 Hunk 级暂存 | 需 patch 重组 + `git apply --cached`，且要处理"部分 hunk 应用后 index 与工作区重新计算"的回读。本轮先把解析基座打好 | WP5.3 |
| 单文件 diff 未做虚拟化 | `ScrollViewer + ItemsControl` 才能横向滚动（代码行不该软换行，否则行号列错位）。代价是超大文件（数千行）可能卡顿，但 `GetDiffAsync` 只取单个文件 | 后续可换 `VirtualizingStackPanel` + 固定行高 |
| 无提交历史视图 | 侧栏「历史」仍禁用，tooltip 写明「WP5.3 之后开放」。不把它伪装成已交付 | WP5.4 |
| 不做 Push / Pull | 网络操作涉及凭据与代理，与"本地提交"是完全不同的问题域 | 未排期 |
| 冲突只能提示，不能解决 | 三方 diff 编辑器是独立课题；当前提示"需在外部解决"，并禁掉提交按钮 | 未排期 |

## 5. 遗留与下一步

1. **WP5.3 Hunk 级暂存**：基座已具备（`DiffHunk` 有完整行与行号）。做法是按 hunk 切 patch → 重组 → `git apply --cached`，然后回读工作区确认。
2. **提交历史（WP5.4）**：`git log` 解析 + 侧栏「历史」启用。与变更页共享 `ClInterop` 的进程封装。
3. **详情页联动**：提交后已经会刷新详情页的 Git 摘要（`LoadProjectFactsAsync`），但仓库页的汇总不刷新——用户切过去才会重查，可以接受。
